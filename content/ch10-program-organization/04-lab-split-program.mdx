## 任务

> 下面这个程序能跑、结果也对，但它把所有东西都堆在 `main` 里，还用了一个全局变量。
> 请把它整理成惯例顺序的版本：包含 → 宏 → 类型 → 函数原型 → `main` → 各函数实现。
> 要求整理后的**输出和现在逐字相同**。

```c
#include <stdio.h>

int total;

int main(void)
{
    int s1 = 80, s2 = 95, s3 = 67;
    int best;

    total = s1 + s2 + s3;
    printf("total = %d\n", total);
    printf("average = %d\n", total / 3);

    best = s1;
    if (s2 > best) best = s2;
    if (s3 > best) best = s3;
    printf("best = %d\n", best);
    return 0;
}
```

期望输出是三行：

```
total = 242
average = 80
best = 95
```

## 拆解

**第 1 步：先用一句话说出这段程序在干什么**

「拿三个分数，输出总分、平均分、最高分。」这句话里已经藏着三个动作了——是三个，不是一件。

**第 2 步：给每个动作起名字**

| 动作 | 名字 |
|---|---|
| 求三个数的和 | `sum_of` |
| 求三个数的平均 | `average_of` |
| 求三个数里最大的 | `max_of` |

名字起好了，函数长什么样基本就定了：三个数进去，一个数出来。这也是这一章那句结论的意思——重构的第一步是**起名字**，不是改算法。

**第 3 步：把每样东西安排到六个区段里**

| 乱序版里的东西 | 它的问题 | 整理后放在哪 |
|---|---|---|
| `#include <stdio.h>` | 位置本来就对 | 区段 1 包含 |
| 写死的 `3` | 换个地方看就不知道这个 3 是什么 | 区段 2 宏，写成 `COUNT` |
| 三个分数 | 是「分数」这件事不明显 | 区段 3 类型，`typedef int score_t;` |
| 三个函数 | 还没出现 | 区段 4 原型 |
| 三行 `printf` | 没大问题，但被别的代码夹在中间 | 区段 5 `main`，只留这三行 |
| 求和的代码 | 混在 `main` 里，读不出这是「一件事」 | 区段 6，`sum_of` |
| 求平均的代码 | 同上 | 区段 6，`average_of` |
| 求最大值的 if | 同上，而且 `best` 只在 `main` 里用 | 区段 6，`max_of`；`best` 改成它的局部变量 |
| 全局 `int total;` | 只有 `main` 用它，不配当全局 | **删掉**，改成 `sum_of` 的返回值 |

最后一行是这个练习里最值得注意的地方：那个全局变量不是被「换个位置放好」，而是**被消掉了**。它只被 `main` 用到，所以用返回值就足够——这也是上一节那条判据的应用：只被一个地方用到的变量，本来就该是局部的。

**第 4 步：确认行为没变**

要盯住三件事，它们一样都不能动：

1. 总分还是三个数相加。
2. 平均分还是**整数除法**——`242 / 3` 得 80，不是 80.67，小数部分直接被丢掉。
3. 最大值的比较顺序不变：先跟 `s2` 比，再跟 `s3` 比。

## 整理后

<TryIt title="整理后的版本：输出和乱序版逐字相同">
{`#include <stdio.h>

#define COUNT 3

typedef int score_t;

int sum_of(score_t a, score_t b, score_t c);
int average_of(score_t a, score_t b, score_t c);
score_t max_of(score_t a, score_t b, score_t c);

int main(void)
{
    score_t s1 = 80, s2 = 95, s3 = 67;

    printf("total = %d\\n", sum_of(s1, s2, s3));
    printf("average = %d\\n", average_of(s1, s2, s3));
    printf("best = %d\\n", max_of(s1, s2, s3));
    return 0;
}

int sum_of(score_t a, score_t b, score_t c)
{
    return a + b + c;
}

int average_of(score_t a, score_t b, score_t c)
{
    return (a + b + c) / COUNT;
}

score_t max_of(score_t a, score_t b, score_t c)
{
    score_t best = a;

    if (b > best) {
        best = b;
    }
    if (c > best) {
        best = c;
    }
    return best;
}
`}
</TryIt>

## 为什么输出一定一样

重构改的是**代码长什么样**，不是**程序算什么**。这次的整理只做了三件事：

1. 把 `main` 里的三段逻辑搬到三个函数里（搬的时候一个字都没改）。
2. 把只在一个地方用到的全局变量改成返回值。
3. 把 `3` 和分数类型换成有名字的 `COUNT` 和 `score_t`。

三个函数算的还是原来的式子和原来的顺序，所以输出必然相同。反过来说，这也是检查自己有没有「整理过头」的方法：

> 整理前把输出抄下来（或者直接跑一遍存住），整理后逐字对照。
> 只要有一个字符不同——比如平均分突然变成 80.67——你改的就不是代码结构，而是程序行为。

## 自己动手

1. 把三个分数改成 `70`、`85`、`100`，两个版本各跑一遍，输出的三行应该仍然一模一样（总分 255、平均 85、最高 100）。
2. 再试 `70`、`85`、`99`：总分 254，平均分那一行会打出 84——因为 `254 / 3` 在整数除法里是 84，不是 84.67。**如果哪个版本打出了 84.67，说明它在整理时把 `/ COUNT` 改成了浮点除法**，这就不是重构了。

<Pitfall title="整理时顺手优化了逻辑">
  最常见的「优化」是把 `total / COUNT` 改成 `total / 3.0`，理由通常是「这样更准确」。
  **判据**：整理前后各跑一次，输出逐字对照。出现小数、多一位、少一个空格，都说明你改的是行为。
  想改行为可以，但那是另一件事——先让重构落地，再单独改需求。
</Pitfall>

<Pitfall title="改了名字却没改全">
  把 `total` 换成 `sum_of(...)` 之后，忘了删掉原来引用 `total` 的那一行，编译器会说这个名字没声明。
  **判据**：报错里那个 `undeclared`（未声明）的名字，就是漏改的地方。一次只改一个名字，改完就编译一次。
</Pitfall>

<Pitfall title="整理成「另一个全局变量」">
  如果整理完 `max_of` 里还是直接读写外部的变量，那只是把乱搬了个家。
  **判据**：整理后再看一眼函数外面的变量——只要还有一个只被 `main` 用到的，它就应该变成返回值，而不是留在原地。
</Pitfall>

## 这一节的结论

这次动手课做的事，和「加功能」正好相反：程序的行为一点没变，变的只是它的形状。
你给已有逻辑起了名字、排了位置，还删掉了一个本来就不该存在的全局变量。
以后再遇到一个不敢改的长函数，就按这个顺序来：**先说清它在干什么，再起名字，再排位置，最后逐字核对输出。**
第 10 章到这里结束。下一章是本课程最重的一章——指针。它没有你想象的那么玄：
指针就是一个存地址的变量，读懂它，前面所有的数组和函数都会重新变得清楚。
