<KeyPoint>
  `&&` 和 `||` 会短路：左边一旦能定结果，右边根本不执行——这既能省事也能埋雷。
  所以写条件时，顺序不只是风格问题，它会改变程序的运行结果。
</KeyPoint>

## 三个运算符

| 运算符 | 读作 | 什么时候为真 | 例子 |
|---|---|---|---|
| `&&` | 并且 | 两边都真才真 | `age >= 18 && age <= 60` |
| `||` | 或者 | 有一边真就真 | `x == 0 || y == 0` |
| `!` | 不 | 取反：真变假、假变真 | `!done` |

它们和关系运算符一样，算出来的还是整数 `1` 或 `0`。
把它们用在 `if` 里，就是把好几个判断题合成一个：

```c
if (score >= 60 && score <= 100)
    printf("分数有效\\n");
```

## 短路：左边能定结果，右边就不算

`&&` 和 `||` 都有短路（short-circuit）行为：

- `A && B`：如果 `A` 是假，整个表达式一定是假 → **`B` 根本不执行**
- `A || B`：如果 `A` 是真，整个表达式一定是真 → **`B` 根本不执行**

短路本身是好事：它省掉了一次没必要的计算，还让「先检查再使用」这种写法成为可能：

```c
if (n != 0 && 100 / n > 5)
    printf("big\\n");
```

`n` 是 0 时，左边 `n != 0` 是假，右边的 `100 / n` 不会执行，所以不会发生除零。
如果你把顺序反过来写成 `100 / n > 5 && n != 0`，`n` 为 0 时程序在第一个条件那里就崩了——
**右边的检查来得太晚了**。

## 埋雷的那一面：副作用被跳过

短路会「跳过」右边，那如果右边带着副作用（`++`、赋值、`scanf`），它可能一次都没执行：

<TryIt title="短路把 ++i 吃掉了">
{`#include <stdio.h>

int main(void)
{
    int i = 0;

    if (i != 0 && ++i > 0)
        printf("A i=%d\\n", i);
    else
        printf("B i=%d\\n", i);
    return 0;
}
`}
</TryIt>

输出是 `B i=0`：左边 `i != 0` 为假，`&&` 直接短路，`++i` 没有机会执行，所以 `i` 还是 0。
这类 bug 很难查——你盯着代码看，`++i` 明明写着，但运行时它就是没发生。

<Callout type="tip" title="条件里只读，不改">
  判断条件里只放「读」（比较、取值），不放「改」（`++`、`--`、赋值、`scanf`）。
  副作用挪到条件外面写，短路就再也伤不到你。
</Callout>

<Pitfall title="用 & 和 | 代替 && 和 ||">
  `&` 和 `|` 是**按位**运算符，它们**不短路**：两边都会老老实实算一遍。
  判据：在 `if` 的条件里看到单个 `&` 或单个 `|`，先怀疑是写错了——除非你真的在处理二进制位。
  顺带一提，`if (a & b)` 在 `a`、`b` 都是 `1` 或 `0` 时结果和 `&&` 一样，所以这个错**能跑通**，更难被发现。
</Pitfall>

<Pitfall title="以为 && 两边一定会求值">
  用 `&&` 串起两个函数调用，然后奇怪为什么第二个函数的日志没打印——
  去检查第一个函数是不是返回了假（或 0）。这不是编译器出问题，是短路在按规则工作。
</Pitfall>

## 这一节的结论

`&&` 和 `||` 不只是「组合条件」的语法糖，它们还规定了**求值顺序**：
左边能定结果，右边就不执行。把「先排除危险值」的条件写在左边，是它的正面用法；
把带副作用的表达式放在右边，就是它埋的雷。
