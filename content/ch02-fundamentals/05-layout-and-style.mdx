## 一条最省事的规则

**每个 `{` 让内容多缩进一级，每个 `}` 让缩进退回一级。**

```c
#include <stdio.h>

int main(void)
{
    int n = 3;

    if (n > 0) {
        printf("正数\n");
        n = n - 1;
    }

    printf("结束\n");
    return 0;
}
```

缩进用**空格还是 Tab** 不重要（选一种别混用），一级用 **4 个空格**是 C 社区最常见的。

## 空行用来分组

空行不是为了「好看」，它是在说「下面这几行和上面不是一组」：

```c
int a, b;

scanf("%d %d", &a, &b);

printf("%d\n", a + b);
```

读的时候，眼睛会自然地在空行处停顿——这就是它的价值。

## 缩进真的能帮你找错

看这两段代码（逻辑完全一样）：

```c
/* 缩进乱的版本 */
int main(void) {
int score = 85;
if (score >= 60) {
printf("通过\n");
} else {
printf("不通过\n");
}
return 0;
}
```

```c
/* 缩进对的版本 */
int main(void)
{
    int score = 85;

    if (score >= 60) {
        printf("通过\n");
    } else {
        printf("不通过\n");
    }

    return 0;
}
```

当括号少了一个、或者 `else` 挂错了 `if` 时，**只有第二种排版能让你一眼看出来**。
这不是审美问题，是排查效率问题。

## 关于警告：让它归零

编译器给的 `warning` 是「我已经发现问题，但还愿意放你过去」。比如：

```
warning: implicit declaration of function 'prinft'
warning: unused variable 'total'
```

常见的警告几乎都是真 bug 的前兆：函数名拼错、变量声明了没用（可能本该用却没用到）、
类型转换会丢精度……**养成习惯：让编译输出里 warning 数为 0**，而不是「能跑就行」。

<Callout type="tip" title="一个立刻能用的习惯">
  写完一个函数就编译一次，别等写完 200 行再编译。
  一次只面对一两个错误，比一次面对二十个错误轻松十倍。
</Callout>

<Pitfall title="靠缩进「假装」代码块">
  ```c
  if (n > 0)
      printf("A\n");
      printf("B\n");   /* ❌ 这行其实不在 if 里面！缩进骗了你 */
  ```
  C 用**花括号**划分代码块，不用缩进。单语句可以省略花括号，但加上更安全——
  以后想再加一行时不会踩这个坑。
</Pitfall>

<Pitfall title="行太长">
  一行超过 100 个字符就该换行，并在续行处多缩进一级。
  横着读代码要左右滚动，是最消耗耐心的阅读体验。
</Pitfall>
